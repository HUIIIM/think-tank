# 决策记录模板

> 每次 think-tank 运行收敛后，CEO 终裁输出一份决策记录，存档为决策史。
> 格式对齐公司决策记录的条目体例；引用历史结论必须标注其记录编号。

```markdown
## <记录编号>（<终裁类型>，<日期>；<议题一句话>）

- 任务来源：<谁提的建议 / 哪个 D 的后续 / 什么触发器>。
- 门禁 0：<通过/驳回>——<一句话主题关系>。
- Verdict：<接 / 改 / 驳>——<一句话结论>。
- 三队观点：
  - 红队：<一句话立场>——<最强质疑>。
  - 蓝队：<一句话立场>——<对 Miao 的损益账>。
  - 白队：<一句话立场>——<执行链要点>。
  - 意外视角（<角色>）：<一句话立场>。
- 总协调建议：<裁决书一句话结论>；<真分歧裁决摘要>。
- CEO 终裁：<维持 / 修改 / 推翻>——<终裁理由>。
  - （若修改/推翻：改了什么、为什么改、证据是什么。按「意见为建议」规则：董事长意见采纳/驳回均需写理由。）
- 依据：<引用的记录编号 / 研究报告 / 数据口径>。
- 复盘点：<什么证据出现时提前重估本决定>。
- 置信度：<0–100>%——<CEO 对本 Verdict 正确的把握；参考裁决书 Collect 阶段各方置信度>。
- 预期结果：<到复评日期应当看到什么：指标＋数值或可核对的事实；写成事后能判"达到/未达到"的句子>。
- 复评日期：<YYYY-MM-DD>
- 实际结果：待复评
- 状态：<提议 / 已采纳 / 已取代（→ 新记录编号）/ 已撤销>
- 执行跟进项（如有，按报告问责规则）：改什么 / 验收 / 责任人 / 截止日期。
```

## 填写纪律

1. **Verdict 三选一**：接 / 改 / 驳。"再看看""待定"不是 verdict，打回重议。
2. **每条有依据**：终裁理由必须挂证据或记录编号引用；"我觉得"不算依据。
3. **红队质疑全回应**：裁决书里红队提了几条，这里就要有几条回应，不许吞。
4. **复盘点必填**：触发提前重估的条件写在"复盘点"，日期写在"复评日期"。没有复盘点的决策 = 假设自己永远正确，不许存档。
5. **试运行标注**：skill 自测/ dry-run 产出的记录，标题必须标注 [试运行]，不进正式决策日志，避免污染真实决策史。
6. **结果回路**：
   - "复评日期"只写一个 `YYYY-MM-DD` 日期，不加别的字，供脚本读取。
   - 新记录的"实际结果"一律写"待复评"。到期复评时改写为"达到 / 未达到 / 部分达到——<证据或记录编号>"，并对照"预期结果"和"置信度"：高置信度却未达到，要在复评记录里写清当时漏看了什么。
   - 被新决定取代时，把"状态"改为"已取代（→ 新记录编号）"，原记录保留不删。
7. **存档与到期提醒**：
   - 本仓库公开，不存放真实决策记录。真实记录存放在私有归档目录，每条记录一个 `.md` 文件；归档目录只放记录文件（说明文档放在别处，否则提到 Verdict 的说明会被当成写坏的记录报错）。字段行用 `- ` 或 `* ` 开头，不缩进。标题只认行首 1–6 个 `#` 加空格的写法（setext 标题、缩进的标题、`#` 后不加空格都不算，像标题却不是的行会报错）。每条记录的 Verdict 只归它所在的最深标题；"复评日期""实际结果""状态"各写恰好一次，直接写在记录标题下、任何子标题之前，写成行首 `- 字段名：值`。缺写、重复、写在引用或表格里都会报错；子小节、同级小节、上面的文档标题、代码块和 HTML 注释里的同名字段一律不读（子小节可能在讲另一条记录），只写在那里就等于缺写。只有以"达到 / 未达到 / 部分达到"开头的实际结果才算已复评，只有以"已取代 / 已撤销"开头的状态才算关闭；写法拿不准时一律按待复评提醒。
   - `python3 scripts/review_due.py <归档目录>` 列出已到复评日期、仍"待复评"且状态不是已取代/已撤销的记录；缺少或写错"复评日期"的记录、写了 Verdict 却读不出记录的文件、无法按 UTF-8 读取的文件都报为错误。
   - 加 `--strict` 时，只要有上述任一项就以退出码 1 结束，可接入定时任务。
