## 执行记录

### 待决策事项（输入）

**是否把 trust-rule 式 lasting allow 机制排进 10-18 开发计划。**

背景（实证依据）：
- 2026-10-03 实证：从聊天上下文直接执行 IG 写操作会触发 runtime approval 确认卡去问 Miao
  （10-02 23:33 发帖返回 `userConfirmationRequired=true`；10-03 00:01 子代理发 DM 触发确认卡），
  而 detached 定时任务持有 lasting allow，全程静默发送。
- Miao 亲口："以后不要我在授权ins了""我说了几次了"。
- 已有铁律：所有 IG 写操作只走已获长期授权的定时任务，绝不从聊天上下文直接执行。
- 提案：把这一经验机制化——"trust-rule 式 lasting allow"：对**已授权的任务类别**
  （如 IG DM 下发、定时内容发布）授予长期许可，同类后续执行免逐次审批，
  附带 scope 边界、审计日志、一键撤销；排进 10-18 开发计划。

---

### 一、开场定义

- **决什么**：是否把"trust-rule 式 lasting allow 机制"（定义见下）排进 10-18 开发计划。
- **载荷词定义**：
  - `trust-rule`：一条可审计的授权规则——"某类动作在某 scope 内，授予长期执行许可"，不是一次性口头允许。
  - `lasting allow`：许可的时效形态——一次授予、长期有效，直到被显式撤销；区别于"每次执行前弹确认卡"的逐次审批。
  - `机制`：规则的载体——scope 白名单（哪类动作）＋ 审计日志（谁何时执行了什么）＋ 一键撤销（随时收回）＋ 定期复核（过期重审）。四件缺一不可，否则不叫机制，叫口头约定。
  - `10-18 开发计划`：2026-10-18 为交付截止的开发排期窗口。
- **裁决选项**：接（排进 10-18，按提案四件套开发）/ 改（排进但改 scope 或拆期）/ 驳（不排，维持现状：靠各定时任务各自持有隐式许可）。
- **门禁 0**：通过——直接关系：减少 Miao 被重复打扰（"不要再问我了"是他的亲口指令），属于运营他的人生的效率事项。

### 二、张力网络

| 视角 | 一句话立场 | 为什么需要他 |
|---|---|---|
| 红队（风险视角） | 长期免审批 = 长期免监督，失控时发现即已晚 | 专挑"静默执行"的失控链：scope 蠕变、日志无人看、撤销失灵 |
| 蓝队（Miao 视角） | 他亲口说了"不要再问我"，重复确认卡是纯成本 | 只算他的人生账：每次确认卡打断他一次，静默是他要的体验 |
| 白队（工程视角） | 四件套里 scope 边界和撤销是最难的，先啃硬的 | 不谈愿景，只谈 10-18 前能不能交付出可用的最小闭环 |
| 意外视角（平台规则视角） | IG/X 的平台自动化政策不认"内部授权"，封号风险不看你内部有没有 trust-rule | 三队都在"内部效率"里打转，需要一个人站在平台外面看 |

### 三、辩证过程

#### 三队独立初稿（互不可见）

**红队初稿**：立场：**改**——机制可以进，但 scope 必须先收敛到"只读/只发已审内容"，且审计日志必须有人看（无人看的日志=没有日志）。
论据：[1] [实证] 10-03 确认卡事故证明：写操作一旦静默，出错时 Miao 是最后一个知道的人。[2] [推断] lasting allow 的 scope 会随时间蠕变——今天批的是"发 DM"，三个月后可能被理解为"代他社交"。[3] [公开] 平台方对自动化账号的处罚不看内部授权链，只看行为模式。
攻击预告：蓝队会说"他亲口不要再问"；我的回应：他不要的是"重复问"，不是"永远不问"——出事时的问和日常的问是两回事。

**蓝队初稿**：立场：**接**——排进 10-18，一天都不要拖。
论据：[1] [实证] Miao 原话"以后不要我在授权ins了""我说了几次了"——重复打扰已造成明确负体验。[2] [推断] 每次确认卡都是一次"把他拉回执行细节"的税，与他"只管花钱审批"的授权定位冲突。[3] [实证] detached 定时任务已实证可静默运行——机制化只是把已验证的实践写成规则，风险增量≈0。
攻击预告：红队会谈失控；我的回应：失控的前提是"没人看"，而审计日志+定期复核正是提案四件套里的标配——红队的担心恰好是提案已经回答了的。

**白队初稿**：立场：**改**——排进，但拆两期：10-18 只交付"scope 白名单＋审计日志＋一键撤销"最小闭环，定期复核进第二期。
论据：[1] [推断] 四件套里 scope 白名单的粒度定义（动作×对象×频率上限）是主要工作量，10-18 全量交付四件套排期偏紧。[2] [实证] 现有 cron 体系已有任务级日志，审计日志可复用改造，成本可控。[3] [推断] 一键撤销必须做成"一处撤销、全线生效"，分散在各任务里的撤销=没有撤销。
攻击预告：蓝队会催"一天别拖"；我的回应：拖的不是机制，是"四件套一次全上"的贪心——最小闭环 10-18 可交付，全量是排期自杀。

**意外视角（平台规则）初稿**：立场：**改**——机制内部可以建，但必须加一条"平台行为指纹"约束。
论据：[1] [公开] IG 对非官方 API 自动化的容忍基于行为模式（频率/时段/内容重复度），内部授权书在封号申诉时权重≈0。[2] [推断] lasting allow 让执行更静默、更规律——恰好是自动化检测最喜欢的行为指纹。[3] [实证] 现有 IG 发布已走官方 CLI 路径，风险敞口主要在频率和内容雷同，不在"有没有内部许可"。
攻击预告：三队会把我当"泼冷水"；我的回应：我不是反对机制，我是要求机制里必须有名为"平台侧行为约束"的第五件——否则内部越顺滑，外部死得越快。

#### 第 1 轮辩证

**红队** [反驳] 蓝队"风险增量≈0"不成立。detached 任务静默运行是**事实**，但那是"单个任务、单点许可"；trust-rule 是把单点许可**泛化成类别许可**——从"这个任务可以发"变成"这类动作都可以发"，授权半径扩大了一个数量级，风险增量≠0。
一句话：单点许可变类别许可，授权半径扩大十倍，风险不是零。

**蓝队** [补充] 接受红队的半径批评，但半径大不等于失控——提案四件套里的 scope 白名单正是用来**给半径划边界**的。没有 trust-rule 的今天，半径其实更大：每个定时任务各自拿着隐式许可，无统一 scope、无统一撤销。机制化是**收敛**半径，不是放大。
一句话：今天各任务隐式许可更散，机制化是收紧不是放开。

**白队** [修正] 蓝队"收敛半径"的前提是 scope 白名单先行——而这正是我要求拆两期的原因。10-18 最小闭环必须包含 scope 白名单 v1（动作×对象×频率上限三维），否则第一期交付的"lasting allow"就是没边界的许可，红队的噩梦成真。
一句话：scope 白名单必须进第一期，没边界的许可不能上线。

**意外视角** [质疑] 三队都在争"内部半径"，没人回答我的第五件：平台行为指纹约束进不进第一期？白队的三维 scope（动作×对象×频率）里，"频率上限"如果只从内部效率定（比如每小时 50 条 DM），平台侧可能已经是封号线。频率上限必须**先查平台公开政策与实证**再定，不是内部拍脑袋。
一句话：频率上限得按平台政策定，内部效率说了不算。

**主持人第 1 轮输出**：

1. **核心争议点**：lasting allow 到底是"收敛半径"（蓝队）还是"放大半径"（红队）——取决于 scope 白名单是否先行且有效。这是全场最深的裂缝：双方都同意要机制，分歧在"机制的默认状态是紧还是松"。
2. **ASCII 框架图**：
```

                      |
        +-------------+-------------+
        |                           |
  scope 先行（紧默认）         先上线后补 scope（松默认）
        |                           |
  蓝队：收敛半径               红队噩梦：类别许可
  白队：三维 scope v1          无边界静默执行
  进第一期                     scope 蠕变 → 失控
        |                           |
        +------> 下一轮问题 <--------+
```
3. **下一层问题**：scope 白名单 v1 的三维（动作×对象×频率）里，每一维的"紧默认"具体是什么？以及平台行为指纹约束由谁、在何时、以什么证据定？

#### 第 2 轮辩证

**白队** [陈述] 回答上一轮问题。三维紧默认 v1：① 动作维：只含"已终审内容的发布/发送"，**排除**花钱类动作（D460 硬保留，永不进白名单）、排除未终审的新内容形态；② 对象维：仅限已获长期授权的账号与任务，新增账号/任务走增补审批；③ 频率维：取"平台公开政策限额"与"历史 30 天实证峰值"二者之**低**，由意外视角提供政策基线。
一句话：三维紧默认——只发已终审内容、只认已授权账号、频率取政策与实证二者之低。

**意外视角** [补充] 接受白队的三维框架，补充证据义务：频率基线必须附来源（平台政策原文链接或条款编号＋历史实证数据），写进 scope 白名单文档；任一平台政策变更 → scope 自动冻结待复核（冻结是默认动作，不等待人工发现）。
一句话：频率基线要附政策出处，政策一变 scope 自动冻结。

**红队** [修正] 白队+意外视角的方案回答了我 70% 的担心。剩下 30%：审计日志"有人看"。我要求第一期交付必须包含"异常告警"——不是等人工翻日志，而是 scope 外动作尝试、频率逼近上限 80%、撤销后仍有执行尝试三类事件**主动告警**。无人看的日志=没有日志，告警是日志的嘴。
一句话：日志必须配三类主动告警，否则等于没有日志。

**蓝队** [综合] 三队已收敛到"紧默认＋三维 scope＋告警"的第一期。我只守一条底线：10-18 交付后，Miao 的确认卡打扰必须**实质性下降**（以"每周因重复授权被打扰次数"为指标，目标降到 0）。如果机制上线了他还在被问，等于没建。定期复核（原第四件）我同意进第二期，但第二期的 deadline 必须现在就定（11-01），不许"以后再说"。
一句话：验收指标是他的打扰次数归零，复核二期 deadline 定死 11-01。

**主持人第 2 轮输出**：

1. **核心争议点**：已从"紧还是松"收敛为"第一期装多少"——四方一致同意紧默认＋三维 scope＋三类告警进第一期；唯一未决是定期复核进一期还是二期（蓝队要 deadline 锁死，白队要拆期保交付）。

### 四、总协调裁决书

**一句话结论**：**改**——排进 10-18，但只交付最小闭环（一期）；定期复核拆进二期，deadline 锁 11-01。

**三队共识（4/4）**：
1. lasting allow 机制化是"收敛半径"而非"放大半径"——前提是 scope 白名单先行且紧默认（4/4 同意）。
2. 花钱类动作永不进白名单（D460 硬保留）；只含已终审内容的发布/发送（4/4 同意）。
3. 频率上限取平台政策与历史实证二者之低，且附政策出处；政策变更 scope 自动冻结（4/4 同意）。
4. 审计日志必须配三类主动告警（scope 外尝试/频率达 80%/撤销后仍执行），无人看的日志等于没有（4/4 同意）。

**真分歧裁决**：
- 分歧一（红队 vs 蓝队：半径放大还是收敛）：判蓝队胜——但前提是白队的"scope 先行"为硬性前置条件。若 scope 白名单 v1 未交付，lasting allow 不得上线任何新类别。
- 分歧二（白队 vs 蓝队：一期装多少）：判白队胜——四件套一次全上是排期自杀；定期复核进二期。
- 分歧三（意外视角新增第五件）：接——平台行为指纹约束并入一期 scope 白名单的频率维，不单独成件。

**红队质疑逐条回应**：
1. "类别许可半径扩大十倍"→ 回应：成立，故 scope 白名单为上线硬前置，无 scope 不上线。
2. "scope 蠕变"→ 回应：对象维"新增账号/任务走增补审批"＋政策变更自动冻结，双锁。
3. "日志无人看"→ 回应：成立，故三类主动告警进一期，告警直达值守通道。

**数字口径**：一期交付物 4 件（scope 白名单 v1 文档/审计日志改造/三类告警/一键撤销）；验收指标：Miao 每周因重复授权被打扰次数 → 0；二期 deadline：2026-11-01。

**未决项＋复盘触发**：若一期交付后出现 scope 外执行绕过告警、或平台政策收紧导致冻结，触发复评（走 D107，不自动生效）。
